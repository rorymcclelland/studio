# 0015 Studio's own sign-in: sessions, email links, the mailer, and no dev mode

**Date:** 27 October 2026. **Status:** accepted (built in Sprint 6: N-2 and N-3). Supersedes the sign-in parts of 0001 and 0010 (Supabase magic links, Supabase's admin API for invites, `AUTH_MODE=dev`). The Neon parts of Sprint 6 (N-1, N-4 to N-7) are recorded separately.

**Context.** Sprint 6 moves Studio from Supabase to Neon (docs/refinement/sprint-6.md). Sign-in was the only real Supabase dependency: magic links that reached team members only, and the admin API minting a sign-in for each invite. Rory chose Studio's own sessions (Q1) and sign-in links sent by Resend from a mcclelland.info subdomain (Q2). Invite tokens were already random, hashed and single use, so most of the pattern existed.

**Decision.**
- **Sessions.** A session is 32 random bytes (base64url, 43 characters) in the `cs_session` cookie: httpOnly, SameSite=Lax, path `/`, 30 days, Secure except on plain local http. Only its SHA-256 is stored, in `auth.sessions` (id, user_id, token_hash, created_at, last_seen_at, expires_at). A session used more than a day after it was last seen is extended to 30 days from then; the proxy re-sets the cookie's lifetime on GET requests, so the cookie and the row age together. Sign-out deletes the row and the cookie; the same cookie, replayed, is signed out. Every request still checks the allow-list or `is_invited()`, so revoking someone, or taking them off `ALLOWED_EMAILS`, signs them out on their next request; revoking also deletes their sessions and marks their unused sign-in links used, in the same transaction.
- **Sign-in links.** /signin takes an address and always gives the same reply ("If that address has access, we've sent a sign-in link..."), at once: the access check, the limits and the email run after the response (`after()`), so neither the words nor the timing say who has access. A link is recorded in `auth.sign_in_tokens` (hash only) for 15 minutes, only for an allow-listed address (the server's flag, since the allow-list is an environment variable) or one with a used, unrevoked invite. Limits: 3 links per address per hour and 30 an hour in all, counted from the same table under an advisory lock, to protect Resend's free quota of 100 a day. The link opens `/signin/link/<token>`, which only shows Continue; the POST uses it (once) and starts a session, so link scanners can't use it up. A used or late link lands on /signin with "This link has expired". `/auth/callback` is gone. Validation refuses control characters (header injection) and addresses over 254 characters.
- **Where links point.** Production links use the production domain (`VERCEL_PROJECT_PRODUCTION_URL`) and previews their deployment address (`VERCEL_URL`), never the request's Host header, so a forged Host can't get Studio to email a link to another site. `APP_URL` overrides both; locally the request's own address is used.
- **Database access.** Both tables are in the `auth` schema, with RLS on and all privileges revoked from `anon` and `authenticated`. The app reaches them only through security-definer functions in `public`, each with `set search_path = ''`:

  | Function | Does | Execute |
  | --- | --- | --- |
  | `lookup_session(token_hash)` | user id and email for a live session; extends it after a day | anon, authenticated |
  | `end_session(token_hash)` | sign-out | anon, authenticated |
  | `request_sign_in(email, token_hash, allow_listed)` | records a link if the address has access and the limits allow; returns whether to send | anon |
  | `use_sign_in(token_hash)` | marks a link used and returns its email; refuses used or expired | anon |
  | `end_sessions_for_email(email)` | revoking: ends sessions and unused links, only for an address the caller invited and which has no access left | authenticated |
  | `start_session(user_id, token_hash, expires_at)` | inserts a session | no app role |

  `start_session` is granted to no app role, so nothing that can run as `anon` or `authenticated` can mint a session for a user id of its choosing; the app calls it on its own connection, only after an invite or a link has been used. Finding or creating the `auth.users` row (id, email, created_at, unchanged) is done the same way, as the old local sign-in did. `auth.users` is not workspace data; every workspace read still goes through `asUser()` (rule 7). The refinement's name `session_user` became `lookup_session`, because `SESSION_USER` is a reserved word in SQL.
- **Invites.** `acceptInvite()` checks the invite, finds or creates the user, redeems the invite and starts a session; no provider and no email. F-18a's New sign-in link on /invites stays: it still works and needs no email.
- **The mailer** (`src/lib/email/`) is one interface with two implementations. Resend over plain `fetch` to `https://api.resend.com/emails` (no SDK), used whenever `VERCEL_ENV=production`, so a missing key fails loudly rather than logging a link; off Vercel it is used only if both `RESEND_API_KEY` and `EMAIL_FROM` are set. The console mailer is used everywhere else (local work, CI, previews): it writes the email, link included, to the server log and keeps the last 200 in memory. The email says what Studio is and that the link works once, for 15 minutes, in plain text and simple HTML. A failed send is logged without the address and the page keeps the same reply.
- **How e2e reads links.** `GET /api/dev/last-sign-in-link?email=...` returns the newest link the console mailer sent to that address and a count, so a test can wait for a new one. It answers 404 on any Vercel deployment (production and previews alike, since previews are reachable from the internet) and whenever the mailer isn't the console. A setup project signs the owner in by email once per run and saves the browser state; specs reuse it, which keeps the suite inside 3 links per address per hour. The e2e global setup also forgets earlier runs' links for `@example.test` addresses on a localhost database, so the suite can be run several times an hour.
- **No dev mode.** `AUTH_MODE=dev`, `SESSION_SECRET` and `dev-session.ts` are gone: local work, CI and e2e use the real sign-in with the console mailer, so the tests exercise the production path. `@supabase/ssr`, `@supabase/supabase-js` and `src/lib/auth/supabase.ts` are removed, and `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` and `SUPABASE_SECRET_KEY` are read nowhere (they stay in Vercel for the 14-day way back; N-7 removes them). `configProblems()` names a missing `RESEND_API_KEY` or `EMAIL_FROM` in production.

**Consequences.** Production needs `RESEND_API_KEY` (Production only, Sensitive) and `EMAIL_FROM` before this is deployed, or every page shows the configuration page naming them; the sending subdomain's DNS records (SPF, DKIM) come first. Everyone is signed out once, when this ships, because Supabase's cookies mean nothing to Studio. Locally, signing in means copying the link from the `npm run dev` log. The in-memory outbox is per server process, which is fine for `next start` and the e2e route but means the route sees only links sent by the same process. The anon role is trusted to be reached only by the app's own server (the Data API is off and Neon has none); `request_sign_in`'s allow-list flag rests on that.
