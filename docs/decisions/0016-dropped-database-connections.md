# 0016 Dropped database connections: patch postgres.js, short-lived pool, one safe retry

**Date:** 29 October 2026. **Status:** accepted. Builds on 0015 Part 1 (Neon's pooled connection).

**Context.** On 29 October, a server action on /campaigns/[id] logged `Uncaught Exception: TypeError: Cannot read properties of null (reading 'write') at Immediate`, then 30 seconds later `write CONNECT_TIMEOUT ...-pooler...:5432`, then `Node.js process exited with exit status: 129`. Earlier that morning a transaction was left idle in transaction holding an advisory lock, as if a process had died mid-transaction. The same code ran for weeks on Supabase's pooler; it began after the move to Neon, whose compute scales to zero after 5 idle minutes and drops its connections, on Vercel Fluid compute, which suspends an instance between requests.

**Cause.** Three bugs in `postgres` 3.4.9 (`src/connection.js`), the latest release; master on GitHub has the same code, and no issue or release note covers it.

1. *A write to a null socket.* When the server closes a connection (a FIN, as Neon's pooler or compute does) while a transaction is open, `closed()` sets `socket = null`, rejects the running query and returns the connection to the pool. `sql.begin()` then runs its rollback (`scope()`'s `catch`, `sql\`rollback\``) through a handler that still holds the closed connection, so `execute()` queues the bytes with `write()`, which schedules `setImmediate(nextWrite)`, and `nextWrite()` calls `socket.write(chunk, fn)` on `null`. The TypeError is thrown from an Immediate, outside any promise, so it is an uncaught exception, and the instance exits.
2. *A connection that never connects again.* `closed()` calls `clearImmediate(nextWriteTimer)` but leaves `nextWriteTimer` and `chunk` set (and after bug 1, `nextWrite()` threw before clearing them). When the pool reuses that connection, `write()` appends the startup message to the stale bytes and, seeing a timer already "scheduled", never flushes: the connect waits for `connect_timeout` (30 s by default) and fails with `CONNECT_TIMEOUT`.

3. *A query that never settles* (found in review). `closed()` rejects the running query but leaves it in `query`. On the next connect, an ErrorResponse during startup (the database refusing connections, say) takes `ErrorResponse()`'s `if (query)` branch and is stored as that dead query's error, so the waiting query is never rejected; the server then closes, `closed()` sees `initial` still set and calls `reconnect()` at once (without updating `closedTime`), and `connectTimer` restarts each attempt, so `CONNECT_TIMEOUT` never fires either: the promise never settles and the instance reconnects in a tight loop. The same `if (initial) return reconnect()` loops for any single server that closes during startup without an error.

Supabase's pooler rarely closed a connection in the middle of a transaction; Neon's scale-to-zero and a suspended instance waking with dead connections make it routine.

**Decision.**
- **Patch postgres.js** with `patch-package` (`patches/postgres+3.4.9.patch`, applied by `postinstall` with `--error-on-fail`; `postgres` pinned to `3.4.9` so the patch always matches). In `src`, `cjs` and `cf`: `execute()` fails a query at once with `CONNECTION_CLOSED` when the socket has gone (returning true, so the pool's queues are left as they are); `nextWrite()` never writes to a null socket; `closed()` forgets the rejected query (`query`, `errorResponse`, `results`, `result`, `rows`), so a failed startup rejects the waiting query; `closed()` reconnects during startup only when this side ended it on purpose (`terminate()`) or another host is left to try, and otherwise fails the waiting query with `CONNECTION_CLOSED`, so there is no reconnect loop; and `closed()` clears `chunk` and `nextWriteTimer`. That last change is defensive: in Node a socket's `close` is emitted after the check phase, so the queued `setImmediate` write normally runs (or, after bug 1, throws) before `closed()`; the stale timer and bytes of bug 2 only follow from bug 1, which the `nextWrite()` guard now prevents, and no test can make the case happen on its own. Returning true from `execute()` on a closed connection is right only for the `begin()` and `reserve()` handlers, the only callers that can hold one (the patch says so); Studio uses `begin()`. Upgrading was not an option (3.4.9 is the newest), and switching drivers was ruled out. Drop the patch when an upstream release fixes both.
- **A short-lived pool** (`src/lib/db/client.ts`): `idle_timeout` 5 s (was 20), `max_lifetime` 5 minutes (default 30 to 60), `connect_timeout` 10 s (default 30). A connection is not kept long enough to meet Neon's 5-minute scale-to-zero, and a cold connect fails in 10 s rather than 30.
- **Keep the instance running until idle connections have closed.** Vercel's `attachDatabasePool` (`@vercel/functions`) does this for other drivers, but its source only recognises pg, mysql2, MariaDB, MongoDB, Redis and Cassandra pools by their shape (an `on('release')` event and known option names); a postgres.js `Sql` has neither and makes it throw "Unsupported database pool type". `keepInstanceUntilIdle()` does the same thing by hand: each `getSql()`, each finished `asUser()`/`asAnon()` and each finished `withSql()` passes Vercel's `waitUntil` a promise that settles 6 s later (one pending at a time), so idle timers fire before the instance is suspended. Outside a Vercel request it does nothing. Next's `after()` was not used: it throws outside a request scope, and the database layer also runs in tests and scripts.
- **Bare statements go through `withSql()`**, which starts the idle wait once they have settled, so a slow cold connect can't outlast it: `createSession`, `findOrCreateUser`, `requestSignInLink` and `/api/health`.
- **Safe retries** (`src/lib/db/scoped.ts`): if `asUser()`/`asAnon()` fails with a connection error before the caller's function has started, it is retried on another connection. A connection that has died (`CONNECTION_CLOSED`, `CONNECTION_DESTROYED`, `ECONNRESET`, `EPIPE`, SQLSTATE class 08, 57P01 to 57P03) is retried up to the pool's size, since every idle connection may be dead after a suspension; a connect that failed (`CONNECT_TIMEOUT`, `ETIMEDOUT`, `ECONNREFUSED`, `ENOTFOUND`, `EAI_AGAIN`, `EHOSTUNREACH`, `ENETUNREACH`) once, since more tries would only multiply a 10 s wait. Once the caller's function has started it is never retried, because it may have written or committed; that request fails with a clean error.
- **`idle_in_transaction_session_timeout = 15s`** is set on the Neon `studio` database for production and preview (outside the repo, 29 October), so a transaction left open by a dying process holds its locks for 15 s, not 5 minutes.
- **No process-level guard.** An `uncaughtException` handler would hide the fault without repairing the connection (bug 2), and could keep a broken process serving.

**Consequences.** `tests/db/dropped-connection.test.ts` puts a TCP proxy between the pool and Postgres: a connection closed mid-transaction now fails that request with `CONNECTION_CLOSED`, throws nothing outside it, and the next request connects at once (without the patch the test sees the TypeError); a connection that died while idle is retried and the caller's function runs once; with every pooled connection dead, the retries reach a fresh one; a refused startup after a mid-transaction drop rejects the next request at once with the server's error and no further connects (without the fix it never settled); a server that closes during startup fails the request after the pool's size plus one tries; and `withSql()` starts the idle wait after its statement. More connects than before (each costs a TLS handshake to London, tens of milliseconds), and an instance stays up about 6 s after its last query, which Fluid bills as memory time. Bare `getSql()` statements (sign-in, sessions, health) are not retried, since some of them consume a token; a stale connection there fails the request cleanly. Not verified here: behaviour under a real Vercel suspension, and whether timers that fall due during a suspension fire before the next request's query on waking.
