# 0015 Neon and Studio's own sign-in

**Date:** 27 October 2026 (sign-in); Neon part added 28 October 2026. **Status:** accepted (built in Sprint 6: N-1 to N-7). Supersedes the Supabase parts of 0001 (Postgres, auth and storage on Supabase; the keep-awake cron) and 0010 (sign-in through Supabase's admin API; previews on a second Supabase project). Their other decisions stand.

Two parts: where the database lives and how its schema is built (Part 1), and how people sign in (Part 2).

## Part 1: the database on Neon (N-1, N-4 to N-7)

**Context.** Supabase's free plan allows two active projects, and Studio's production and preview projects used both, so no other demo app could run. Neon's free plan allows 100 projects, each with its own compute and storage allowance, and an idle project resumes on its own instead of being paused. By Sprint 5 the app used Supabase only for Postgres and sign-in: data access was already plain Postgres through `asUser()`, and the Data API was off (F-12a).

**Decision.**
- **One Neon project per app.** `campaign-studio` (id `misty-moon-16212068`) in AWS Europe (London), `aws-eu-west-2`, beside the functions in `lhr1`. Database `studio`, owned by the role `studio_owner`, which is not a superuser.
- **Three permanent branches.** `production` (the app's data); `ci`, kept empty, the parent of a throwaway branch per CI run (deleted at the end of the run, and set to expire after two hours in case it isn't; one run at a time); `preview`, made from `ci`, migrated, with demo data only, for every Vercel preview (Q3). `ci` and `preview` are never reset from `production`, so no invitee's data reaches a copy.
- **Connections.** The app uses the branch's pooled string (PgBouncer in transaction mode, so prepared statements are off and the one advisory lock is transaction-scoped). The migration runner, CI and the one-off data copy use the direct string. Strings live only in Vercel's environment variables and GitHub's secrets; CI fetches its branch's string from the Neon API and masks it before anything prints.
- **Migrations are files with a ledger.** `db/migrations/` builds every database in name order. The first file (`20261024000000_auth_schema.sql`) makes what Supabase used to provide: the `auth` schema, `auth.users` (id, email, created_at), `auth.uid()`, `auth.role()` and the `anon` and `authenticated` roles, with no superuser needed. `public.schema_migrations` records each file's name and sha256; `scripts/db-migrate.mjs` applies pending files one transaction each and refuses to run if an applied file has changed. Locally and in CI the runner applies them; on Neon, Claude applies them through the Neon connector, one file and its ledger row per `run_sql_transaction` (Rory's answer to Q4), and `scripts/schema-fingerprint.sql` checks the result against a local build.
- **No keep-awake cron.** Neon suspends a branch's compute after 5 minutes idle and resumes it on the next connection; it never pauses the project. `/api/health` stays for the after-deploy Action and for people.
- **Neon's own extras are off.** No Neon Auth (Part 2 is Studio's own), no Data API, and not Neon's Vercel integration (it makes a branch per preview copied from production, which would put invitees' emails in previews and run into the 10-branch limit; Q3). Vercel's `DATABASE_URL` values are set by hand.
- **The way back.** Supabase stays untouched for 14 days after cutover, then Rory pauses and deletes both projects (Q6). The cutover runbook in `docs/hosting.md` says how to go back.

**Consequences.** The first request after 5 idle minutes waits a few hundred milliseconds while compute resumes; the free plan can't keep it on. Free-plan limits to watch: 0.5 GB storage per project (production was 22 MB at the end of Sprint 5; the cutover records the size on Neon), 10 branches and 100 CU-hours a month. The `anon` role is trusted to be reached only by the app's own server, so Neon's Data API must never be turned on for this project. Another demo app copies this set-up (`docs/new-demo-app.md`) in its own Neon project.

## Part 2: Studio's own sign-in (N-2, N-3)

This part was first recorded on 27 October 2026 as "Studio's own sign-in: sessions, email links, the mailer, and no dev mode".

**Context.** Sign-in was the only real Supabase dependency: magic links that reached team members only, and the admin API minting a sign-in for each invite. Rory chose Studio's own sessions (Q1) and sign-in links sent by Resend from a mcclelland.info subdomain (Q2). Invite tokens were already random, hashed and single use, so most of the pattern existed.

**Decision.**
- **Sessions.** A session is 32 random bytes (base64url, 43 characters) in the `cs_session` cookie: httpOnly, SameSite=Lax, path `/`, 30 days, Secure except on plain local http. Only its SHA-256 is stored, in `auth.sessions` (id, user_id, token_hash, created_at, last_seen_at, expires_at). A session used more than a day after it was last seen is extended to 30 days from then; the proxy re-sets the cookie's lifetime on GET requests, so the cookie and the row age together. The proxy can't tell a live cookie from a dead one (that needs the database), so a signed-in page that finds no session for a cookie that is present sends the visitor to `/signin/ended`, which clears the cookie (only if it really signs no one in, so a link from another site can't sign anyone out) and sends them where someone with no cookie goes: the welcome page from /, sign-in from anywhere else (Sprint 6 review). The proxy never renews the cookie on that route. Sign-out deletes the row and the cookie; the same cookie, replayed, is signed out. Every request still checks the allow-list or `is_invited()`, so revoking someone, or taking them off `ALLOWED_EMAILS`, signs them out on their next request; revoking also deletes their sessions and marks their unused sign-in links used, in the same transaction.
- **Sign-in links.** /signin takes an address and always gives the same reply ("If that address has access, we've sent a sign-in link..."), at once: the access check, the limits and the email run after the response (`after()`), so neither the words nor the timing say who has access. A link is recorded in `auth.sign_in_tokens` (hash only) for 15 minutes, only for an allow-listed address (the server's flag, since the allow-list is an environment variable) or one with a used, unrevoked invite. Limits: per address, 3 links an hour and 10 a day; in all, 30 an hour and 80 a day (the daily limits added in the Sprint 6 review, since the hourly ones alone would let someone use up the quota in a few hours). They are counted from the same table under an advisory lock, to protect Resend's free quota of 100 a day; rows are kept for two days, so the daily count always sees every link it needs. The link opens `/signin/link/<token>`, which only shows Continue; the POST uses it (once) and starts a session, so link scanners can't use it up. A used or late link lands on /signin with "This link has expired". `/auth/callback` is gone. Validation refuses control characters (header injection) and addresses over 254 characters.
- **Where links point.** Production links use the production domain (`VERCEL_PROJECT_PRODUCTION_URL`) and previews their deployment address (`VERCEL_URL`), never the request's Host header, so a forged Host can't get Studio to email a link to another site. `APP_URL` overrides both; locally the request's own address is used.
- **Database access.** Both tables are in the `auth` schema, with RLS on and all privileges revoked from `anon` and `authenticated`. The app reaches them only through security-definer functions in `public`, each with `set search_path = ''`:

  | Function | Does | Execute |
  | --- | --- | --- |
  | `lookup_session(token_hash)` | user id and email for a live session; extends it after a day | anon, authenticated |
  | `end_session(token_hash)` | sign-out | anon, authenticated |
  | `request_sign_in(email, token_hash, allow_listed)` | records a link if the address has access and the limits allow; returns whether to send | no app role |
  | `use_sign_in(token_hash)` | marks a link used and returns its email; refuses used or expired | anon |
  | `end_sessions_for_email(email)` | revoking: ends sessions and unused links, only for an address the caller invited and which has no access left | authenticated |
  | `start_session(user_id, token_hash, expires_at)` | inserts a session | no app role |

  `start_session` is granted to no app role, so nothing that can run as `anon` or `authenticated` can mint a session for a user id of its choosing; the app calls it on its own connection, only after an invite or a link has been used. `request_sign_in` trusts its `allow_listed` flag (the allow-list is an environment variable the database can't see), so since the Sprint 6 review (migration `20261029000002_sign_in_review_fixes.sql`) it too is granted to no app role, `PUBLIC` included, and the app calls it on its own connection. Finding or creating the `auth.users` row (id, email, created_at, unchanged) is done the same way, as the old local sign-in did. `auth.users` is not workspace data; every workspace read still goes through `asUser()` (rule 7). The refinement's name `session_user` became `lookup_session`, because `SESSION_USER` is a reserved word in SQL.
- **Invites.** `acceptInvite()` checks the invite, finds or creates the user, redeems the invite and starts a session; no provider and no email. F-18a's New sign-in link on /invites stays: it still works and needs no email.
- **The mailer** (`src/lib/email/`) is one interface with two implementations. Resend over plain `fetch` to `https://api.resend.com/emails` (no SDK), used whenever `VERCEL_ENV=production`, so a missing key fails loudly rather than logging a link; off Vercel it is used only if both `RESEND_API_KEY` and `EMAIL_FROM` are set. The console mailer is used everywhere else (local work, CI, previews): it writes the email, link included, to the server log and keeps the last 200 in memory. The email says what Studio is and that the link works once, for 15 minutes, in plain text and simple HTML. A failed send is logged without the address and the page keeps the same reply: the Resend mailer never logs the recipient, and anything shaped like an address in Resend's error reply, or in any error the sign-in action logs, is replaced with `[address]` (Sprint 6 review).
- **How e2e reads links.** `GET /api/dev/last-sign-in-link?email=...` returns the newest link the console mailer sent to that address and a count, so a test can wait for a new one. It answers 404 on any Vercel deployment (production and previews alike, since previews are reachable from the internet) and whenever the mailer isn't the console. A setup project signs the owner in by email once per run and saves the browser state; specs reuse it, which keeps the suite inside 3 links per address per hour. The e2e global setup also forgets earlier runs' links for `@example.test` addresses on a localhost database, so the suite can be run several times an hour.
- **No dev mode.** `AUTH_MODE=dev`, `SESSION_SECRET` and `dev-session.ts` are gone: local work, CI and e2e use the real sign-in with the console mailer, so the tests exercise the production path. `@supabase/ssr`, `@supabase/supabase-js` and `src/lib/auth/supabase.ts` are removed, and `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` and `SUPABASE_SECRET_KEY` are read nowhere (they stay in Vercel for the 14-day way back; N-7 removes them). `configProblems()` names a missing `RESEND_API_KEY` or `EMAIL_FROM` in production.

**Consequences.** Production needs `RESEND_API_KEY` (Production only, Sensitive) and `EMAIL_FROM` before this is deployed, or every page shows the configuration page naming them; the sending subdomain's DNS records (SPF, DKIM) come first. Everyone is signed out once, when this ships, because Supabase's cookies mean nothing to Studio. Locally, signing in means copying the link from the `npm run dev` log. The in-memory outbox is per server process, which is fine for `next start` and the e2e route but means the route sees only links sent by the same process. The anon role is trusted to be reached only by the app's own server (Supabase's Data API was off, and Neon's is never provisioned). `request_sign_in`'s allow-list flag no longer rests on that: only the app's own connection can call it.

**Update, 5 November 2026 (F-34, with F-29).** CI moves to its own Neon project, `campaign-studio-ci` (`little-shadow-88992377`, London, Postgres 17, history window 1 hour), whose only permanent branch `ci` holds an empty `studio` database. Neon's free plan counts every branch's writes towards one project's 1 GB of storage, and CI's throwaway branches, which rebuild the test database many times a run, filled `campaign-studio`'s allowance in early November (Neon's alert; production itself had written 48 MB in all). A full allowance blocks inserts and updates, so CI could have stopped sign-ins and runs on the live site. In its own project CI can fill only its own allowance. `NEON_API_KEY` becomes a key scoped to that project, so CI can no longer fetch production's connection details (F-29). The `ci` branch in `campaign-studio` is retired and can be deleted. No app data, and no copy of it, is in the CI project.
